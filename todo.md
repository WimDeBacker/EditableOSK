- I.3 **Hold a key down for Windows (found by the owner 2026-10-09):** the keyboard cannot hold a key. A shortcut key sends Win, Space, release in one quick sequence, and a latched sticky Win exists only inside the keyboard (it is added to the *next* key, Windows never sees it held). So "hold Win and press Space several times" (the input-language switcher, Win+Space with three or more languages) does not work, with a shortcut key or with the sticky keys. It needs a real hold: a latched Win is sent to Windows as key-down (`SendInput`, `SendKeysHelper`) and as key-up when it is switched off. Decisions for the owner first:
  - **Which keys:** only Win (the safest, solves the language switcher), or every sticky modifier (Ctrl, Alt, Shift too).
  - **Start menu:** releasing Win without another key in between opens the Start menu; suppress it with an invisible dummy key before the key-up.
  - **Safety:** Win must always be released when the keyboard closes, crashes, loses focus (`Deactivate`) or after a time-out; otherwise Win stays pressed in Windows.
  - **How the user chooses it:** a separate "hold Win" key, or the existing Win sticky key that from then on really holds (this changes the behaviour for people who use sticky keys now).
  - Until then: if Windows has Alt+Shift or Ctrl+Shift switched on for the input language (Settings → Time & language → Typing → Advanced keyboard settings), a Key/Shortcut key `{Alt}{Shift}` or `{Ctrl}{Shift}` already switches it.

### Import of learned words ✓ *(word prediction; was Priority 4, found by the owner 2026-10-07, completed 2026-10-09)*

Keyboard Editor → Word prediction has **Import…** under **Export…**: it **merges** a file made with Export into the words learned on this PC (the owner's decision; "replace" was the first proposal). Counts of words and word pairs are added together, new words, new pairs and candidates are taken over, a candidate that is a word after the merge is dropped, and nothing learned here is removed. Details:
- 4.1 **Merge, with a confirmation question.** `WordDatabase.MergeLearned(basePath, language, file)` reads both overlay files into plain data (`ReadOverlayFile`), adds them (`MergeSaveData`, at most `MaxNextWords` pairs per word, the strongest stay) and writes the overlay through the existing temp file + `File.Replace`, so the old file stays as `.bak`. It runs under the same lock as the periodic save; when the database is loaded, what was learned since the last save is saved first, and afterwards the database is loaded again in the background (`WordDatabase.IsLoadedFor`, `WordPredictionBackend.ReloadIfLoaded`).
- 4.2 **Button** `_btnWPImport` in `KeyboardEditorForm`: an `OpenFileDialog`, the question, the merge, a message with what was added; it is possible before anything has been learned and is off while the database loads.
- 4.3 **Checks:** nothing changes (and the message says why) when the file is missing, is not an overlay (a base database), is unreadable, holds no learned words, was learned on another language, or when this PC's own file cannot be read. **New:** the overlay file now carries the `language` of its database (`language="nl"` on the root element, written by every save and by the merge); files from before that have none and are accepted.
- 4.4 **Strings** `wp: Import…`, `wp: tip import`, `wp: import confirm`, `wp: Import done`, the error texts, in `LanguageManager.cs` and `lang_nl.xml`.
- 4.5 **Tests:** `T_LearnedImport` (files: sums, new words and pairs, candidates, `.bak`, every refusal, the merged file loads, the language is written), `T_KeyboardEditorImport` (the button, the question, the call, the reload, every message, Dutch texts), the Keyboard Editor layout and accelerator guards.
- Not done / known: an overlay from before the language was written cannot be checked against the database's language (the file name `worddb_NL.learned.wfq` says it, but a renamed file does not); the merge adds the frequency of a new word that both PCs learned (it is a count, not a rank); no automatic promotion of candidates whose merged count passes the threshold (they are promoted by the next typing, or with Promote).

### Touch-friendly controls and sectioned editor windows ✓ *(accessibility / UI; was Priority 2, completed 2026-10-06; its step numbers 2.x are kept because tests and documents refer to them)*

Merged from the former Priorities 2 (touch target sizes) and 5 (editor windows too tall), because both change the size of the editor windows: bigger targets make windows taller, so the two must be designed together. **Touch-friendly sizing is the default on every desktop, not a setting** — the software must be easy to use for people with a motor disability.

**Order of work:** 2.4.1 → 2.4.3 (Key Editor, as the pattern) → 2.4.4 → 2.4.5 → 2.4.6 → 2.4.7.

#### 2.1 Requirements

- [x] **2.1.1 Targets** — every clickable control (buttons, colour swatches, the `+` group button, checkboxes, combo boxes, spin buttons, tab/section buttons) is at least 44 × 44 px (WCAG 2.5.5). Before the redesign swatches and the `+` button were 32 × 26 px, standard buttons 34 px (`Fluent.BtnH`), and the spin buttons of `NumericUpDown` only a few pixels wide; the latter are replaced by `[−] value [+]` controls with 44 px buttons.
- [x] **2.1.2 Windows too tall** — Key Editor (~770 px tall, 1,080 px wide before any enlargement) and Group Editor did not fit small or scaled displays; they only scrolled. Reorganise into sections (tabs or a segmented section bar) so each section fits the screen at 44 px targets; pin the live preview and Apply/Cancel so they are always visible.
- [x] **2.1.3 Layout approach — flow/table layout, not hand-positioned controls** — build each section with `TableLayoutPanel` (rows/columns sized `AutoSize`/`Percent`) and `FlowLayoutPanel` (wrapping button rows, e.g. the five mode buttons) inside the existing `AddGroup` cards, instead of computing `Left`/`Top` pixel positions (`gy += ROW_H`). Larger targets, larger fonts and other DPI settings then fit without recomputing coordinates, and a narrower window reflows.
- [x] **2.1.4 Languages (label lengths differ)** — the old layout reserved a fixed label column with a lot of empty space to absorb longer translations (Dutch is longer than English; other languages may be longer still). Flow/table layout makes that space unnecessary: `AutoSize` labels let the label column size to the longest label of the language in use, and long labels wrap (`MaximumSize`) instead of being cut off. If a label column would still become too wide, put the label above its input (a stacked layout needs no label column). Never rely on a fixed pixel width for text.
- [x] **2.1.5 Language test** — pseudo-localisation test: load every dialog with each string expanded by ~40 % and assert no label or button text is clipped (measured text width/height with `TextRenderer.MeasureText` versus the control size) and no control overflows its section. This replaces "leave lots of empty space" with a checked guarantee.
- [x] **2.1.6 Dynamic window size** — the editor windows size themselves from their content instead of a constant (before: `Key Editor` 1080 wide, `Group Editor` 880 × 610, `Keyboard Editor` 940 × 560, wizard 880 × 820, passed to `FluentDialogBase(Size)`). Target behaviour: the preferred size comes from the content (`AutoSize`/`GetPreferredSize` of the section layout, recomputed when the language, font size or DPI changes); it is clamped to the screen's working area (`MaximumSize`) and to a sensible minimum; the user can still resize, and the layout reflows to the new size (`Dock = Fill` sections) instead of leaving controls where they were; content that still does not fit scrolls. The sub-dialogs in `GroupEditorForm` that are `FixedSingle` get the same treatment.
- [x] **2.1.7 Consequences to handle** — validation errors on a hidden section must switch to it (and mark the section); accelerator uniqueness per section/dialog; tab order and arrow-key navigation between sections; layouts were hand-positioned, so each dialog is reworked once, in a single pass.
- [x] **2.1.8 Tests** — extend the accessibility tests to assert a minimum size for every interactive control in the editor dialogs.

#### 2.2 Standard for every window: WCAG 2.1 AAA

The software is for people with a motor disability, and low vision is common with it. Concretely: text ≥ 7 : 1 (1.4.6), boundary of every control and the focus indicator ≥ 3 : 1 (1.4.11), pointer targets ≥ 44 × 44 (2.5.5), full keyboard operation (2.1.3); checked in light AND dark theme. Disabled text is exempt. Wrong colours are caught by `T_ColourContrastAaa`; the gallery shows both themes (`mockup_E*_light_*.png`, `mockup_E*_dark_*.png`).
