### Priority 2 — Touch-friendly controls and sectioned editor windows ▶ *(accessibility / UI)*

Merged from the former Priorities 2 (touch target sizes) and 5 (editor windows too tall), because both change the size of the editor windows: bigger targets make windows taller, so the two must be designed together. **Touch-friendly sizing is the default on every desktop, not a setting** — the software must be easy to use for people with a motor disability.

**Order of work:** 2.4.1 → 2.4.3 (Key Editor, as the pattern) → 2.4.4 → 2.4.5 → 2.4.6 → 2.4.7.

#### 2.1 Requirements

- **2.1.1 Targets** — every clickable control (buttons, colour swatches, the `+` group button, checkboxes, combo boxes, spin buttons, tab/section buttons) is at least 44 × 44 px (WCAG 2.5.5). Before the redesign swatches and the `+` button were 32 × 26 px, standard buttons 34 px (`Fluent.BtnH`), and the spin buttons of `NumericUpDown` only a few pixels wide; the latter are replaced by `[−] value [+]` controls with 44 px buttons.
- **2.1.2 Windows too tall** — Key Editor (~770 px tall, 1,080 px wide before any enlargement) and Group Editor did not fit small or scaled displays; they only scrolled. Reorganise into sections (tabs or a segmented section bar) so each section fits the screen at 44 px targets; pin the live preview and Apply/Cancel so they are always visible.
- **2.1.3 Layout approach — flow/table layout, not hand-positioned controls** — build each section with `TableLayoutPanel` (rows/columns sized `AutoSize`/`Percent`) and `FlowLayoutPanel` (wrapping button rows, e.g. the five mode buttons) inside the existing `AddGroup` cards, instead of computing `Left`/`Top` pixel positions (`gy += ROW_H`). Larger targets, larger fonts and other DPI settings then fit without recomputing coordinates, and a narrower window reflows.
- **2.1.4 Languages (label lengths differ)** — the old layout reserved a fixed label column with a lot of empty space to absorb longer translations (Dutch is longer than English; other languages may be longer still). Flow/table layout makes that space unnecessary: `AutoSize` labels let the label column size to the longest label of the language in use, and long labels wrap (`MaximumSize`) instead of being cut off. If a label column would still become too wide, put the label above its input (a stacked layout needs no label column). Never rely on a fixed pixel width for text.
- **2.1.5 Language test** — pseudo-localisation test: load every dialog with each string expanded by ~40 % and assert no label or button text is clipped (measured text width/height with `TextRenderer.MeasureText` versus the control size) and no control overflows its section. This replaces "leave lots of empty space" with a checked guarantee.
- **2.1.6 Dynamic window size** — the editor windows size themselves from their content instead of a constant (before: `Key Editor` 1080 wide, `Group Editor` 880 × 610, `Keyboard Editor` 940 × 560, wizard 880 × 820, passed to `FluentDialogBase(Size)`). Target behaviour: the preferred size comes from the content (`AutoSize`/`GetPreferredSize` of the section layout, recomputed when the language, font size or DPI changes); it is clamped to the screen's working area (`MaximumSize`) and to a sensible minimum; the user can still resize, and the layout reflows to the new size (`Dock = Fill` sections) instead of leaving controls where they were; content that still does not fit scrolls. The sub-dialogs in `GroupEditorForm` that are `FixedSingle` get the same treatment.
- **2.1.7 Consequences to handle** — validation errors on a hidden section must switch to it (and mark the section); accelerator uniqueness per section/dialog; tab order and arrow-key navigation between sections; layouts were hand-positioned, so each dialog is reworked once, in a single pass.
- **2.1.8 Tests** — extend the accessibility tests to assert a minimum size for every interactive control in the editor dialogs.

#### 2.2 Standard for every window: WCAG 2.1 AAA

The software is for people with a motor disability, and low vision is common with it. Concretely: text ≥ 7 : 1 (1.4.6), boundary of every control and the focus indicator ≥ 3 : 1 (1.4.11), pointer targets ≥ 44 × 44 (2.5.5), full keyboard operation (2.1.3); checked in light AND dark theme. Disabled text is exempt. Wrong colours are caught by `T_ColourContrastAaa`; the gallery shows both themes (`mockup_E*_light_*.png`, `mockup_E*_dark_*.png`).

#### 2.3 Decided Key Editor design ("Option E")

Mock-up in `KeyEditorMockups.cs`, screenshots via `--gallery`.

- **2.3.1 Sections** — two sections, *Key Content* and *Appearance*, plus a **labelled preview card ("Preview") at the top right of both**, next to the section buttons; the footer holds only Cancel / Apply.
- **2.3.2 Key Content** — a grid with one row per layer (Normal / Shift / AltGr) and the columns *Label* (narrow: a key label is short, about 11 characters) | *Action* = type chooser + value + contextual button (*Browse…* / *Record…*); then Key width / Key height side by side. "Send" is renamed **Action**. The five mode buttons are gone: the action type is a `TouchChoiceButton`. Only Text, Key/Shortcut and Layout work per layer today; **Modifier** and **Word prediction** belong to the whole key (a key is a modifier by its *label*, a prediction slot by its main send `wp:`), so on Shift/AltGr they stay in the list, greyed out with the reason ("Whole key only: set it on the Normal layer"). This also replaces the "last focused field" trick of the shared Browse button. *(Word prediction has since been removed from the Shift/AltGr lists entirely; see 2.4.3.3.)*
- **2.3.3 Appearance** — Group (chooser + *Manage Groups…*), Font (chooser with search), Font size + Auto, **Colours as one row of three labelled chips** (Font / Key / Border; hex is not shown), Border thickness.
- **2.3.4 `TouchChoiceButton`** (replaces `ComboBox` everywhere in the editors) — a ≥ 44 px button showing the choice, tap opens a flyout with 44 px rows (56 px with a description line). For lists taller than the screen: height limited to the room above/below the button and to 8 rows, two 44 px arrow strips scroll (press and hold repeats; wheel and keyboard work too), and a search box filters (`Searchable`, for fonts). Keyboard: Enter/Space/Alt+Down open, Up/Down change without opening, Esc closes.
- **2.3.5 Colour chooser** — Windows' `ColorDialog` has no hex box (only H/S/L and R/G/B), and the newer Windows picker with hex exists only in WinUI, so `ColorChip` opens our own flyout: a 24-swatch palette of 44 px (one tap picks), a hex box that applies while typing, and *More colours…* which opens the standard `ColorDialog`. The palette works with the arrow keys.
